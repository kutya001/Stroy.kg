# SPEC.md — Спецификация API аутентификации и UI (Supabase / On-premise)

## 1. Обзор системы аутентификации
Платформа Stroy.kg использует Supabase Auth (или аналогичный кастомный JWT-сервис) для управления идентификацией пользователей. Основным методом входа является аутентификация по email и паролю (`signInWithPassword` / `signUp`). Вход по номеру телефона оставлен как заглушка (stub) для будущей реализации. Администратор входит через email и пароль наравне с остальными пользователями.

## 2. Спецификация API (Supabase Auth / Custom REST)
Методы взаимодействия с сервисом аутентификации:
* `signInWithPassword({ email, password })`: Аутентификация существующего пользователя по email и паролю.
* `signUp({ email, password, options: { data: { role } } })`: Регистрация нового пользователя. Роль передаётся в `raw_user_meta_data`. Триггер `handle_new_user()` автоматически создаёт профиль в таблице `profiles`.
* `signOut()`: Завершение сессии и отзыв токенов.
* `getUser()`: Получение текущего пользователя из сессии.
* `onAuthStateChange()`: Подписка на изменения сессии (SIGNED_IN, SIGNED_OUT).
* **Телефонная авторизация (stub):** `loginWithPhone` в Supabase-режиме возвращает ошибку «Вход по телефону временно недоступен. Используйте почту и пароль.» В mock-режиме работает по-прежнему.
* **Защита:** Rate Limiting на уровне Supabase для защиты от brute-force атак.

## 3. Модуль пользовательского интерфейса (AuthModal)
Процесс аутентификации реализован через `AuthModal` — единую форму входа/регистрации:
* **Переключатель метода:** Табы «Почта» (по умолчанию) и «Телефон» (для mock-режима).
* **Поле email/телефон:** Ввод идентификатора пользователя.
* **Поле пароля:** Обязательное для обоих методов.
* **Чекбокс «Я новый пользователь»:** При активации отображается выбор роли (`consumer`, `supplier`).
* **Логика входа (Supabase):** Сначала `signInWithPassword` → при ошибке `Invalid login credentials` → автоматически `signUp` с выбранной ролью.
* **Логика входа (Mock):** Поиск по email/телефону в mockDb → проверка пароля → вход. Новые пользователи создаются через `createMockUser`.
* **Администратор:** Входит стандартным путём через email `admin@stroy.kg` и пароль `admin123` (Supabase) или `admin` (mock).

## 4. Управление сессией
* Токены (JWT) хранятся в HttpOnly cookies для обеспечения безопасности (XSS защита) и корректной работы Server-Side Rendering (SSR) в Next.js.
* Обновление токенов (refresh) выполняется автоматически middleware-функцией при истечении срока действия access_token.
* Ролевая модель и уровень верификации интегрируются в payload JWT токена для минимизации количества запросов к базе данных при проверке прав доступа.

## 5. Система верификации и гейты доступа
Система имеет 4 уровня верификации, определяющие уровень доступа пользователя (хранится в колонке `verification_level` таблицы `profiles`):
* **Level 0:** Регистрация по email+пароль (Разрешен только просмотр каталога и ленты).
* **Level 1:** Подтверждение email и телефона (stub — заглушка, автоматическое подтверждение при регистрации).
* **Level 2:** Предоставление ИНН / паспортных данных. **Важно:** Взаимодействие с таблицами `requests` (заявки) и `chats` (мессенджер) на уровне RLS (Row Level Security) или API-контроллеров разрешено строго с этого уровня.
* **Level 3:** Подтверждение лицензий / сертификатов (Выдача бейджа "Проверенный").

## 6. SQL скрипты управления данными
Все скрипты расположены в `lib/supabase/`:
* **`migration.sql`** — Идемпотентная миграция схемы БД: ENUM-типы, 7 таблиц, индексы, RLS-политики, триггер автосоздания профиля, seed номенклатурных групп. Безопасна для повторного выполнения.
* **`seed-data.sql`** — Демонстративные данные: 12 пользователей (auth.users + profiles + identities), 6 товаров, 4 заявки, 6 уведомлений, 3 чата, 8 сообщений. Все `ON CONFLICT DO UPDATE`.
* **`cleanup.sql`** — Полная очистка всех таблиц (`TRUNCATE CASCADE`) и `auth.users`.

## 7. Генерация демо-данных (Admin Panel)
В панели администратора (`/admin`) добавлена вкладка «Демо-данные»:
* **Mock-режим:** Кнопка «Сгенерировать демо-данные» вызывает `resetMockData()`, сбрасывая все in-memory хранилища к исходным демо-данным.
* **Supabase-режим:** Информационная панель с описанием SQL-скриптов (`migration.sql`, `seed-data.sql`, `cleanup.sql`) для выполнения через Supabase Dashboard → SQL Editor.
