# SPEC.md — Спецификация API аутентификации и UI (Supabase / On-premise)

## 1. Обзор системы аутентификации
Платформа Stroy.kg использует Supabase Auth (или аналогичный кастомный JWT-сервис) для управления идентификацией пользователей. Основным методом входа является аутентификация по номеру телефона (OTP), с резервной возможностью входа по email и специализированным доступом по паролю для администраторов.

## 2. Спецификация API (Supabase Auth / Custom REST)
Методы взаимодействия с сервисом аутентификации:
* `signInWithOtp({ phone })`: Инициация отправки 6-значного SMS-кода. Номер телефона должен передаваться в формате `+996XXXXXXXXX`.
* `verifyOtp({ phone, token, type: 'sms' })`: Проверка введенного пользователем OTP-кода и генерация сессионных токенов (access_token, refresh_token).
* `updateUser({ phone })`: Инициация смены привязанного номера телефона в профиле пользователя.
* `signOut()`: Завершение сессии и отзыв токенов.
* **Защита:** Внедрение Rate Limiting на уровне API Gateway или настроек Supabase для защиты от SMS-бомбинга.

## 3. Модуль пользовательского интерфейса (AuthModal)
Процесс аутентификации реализован через `AuthModal` со следующими состояниями:
* **Шаг 1 (Ввод данных):** Пользователь вводит номер телефона (+996) и обязательно активирует чекбокс "Согласие с офертой". Кнопка "Отправить код" заблокирована до выполнения этих условий.
* **Шаг 2 (Ввод OTP):** Ввод 6-значного кода с отображением спиннера загрузки при вызове `verifyOtp`.
* **Шаг 3 (Выбор роли - только для новых пользователей):** При отсутствии записи пользователя в БД (регистрация), система переводит его на экран выбора роли (`consumer`, `supplier`, `developer`). Роль фиксируется в таблице `users` (PostgreSQL) и не подлежит самостоятельному изменению.
* **Доступ администратора:** При вводе специального номера `+996555000000` на Шаге 1 система пропускает отправку OTP и запрашивает пароль администратора (аутентификация через `signInWithPassword`).

## 4. Управление сессией
* Токены (JWT) хранятся в HttpOnly cookies для обеспечения безопасности (XSS защита) и корректной работы Server-Side Rendering (SSR) в Next.js.
* Обновление токенов (refresh) выполняется автоматически middleware-функцией при истечении срока действия access_token.
* Ролевая модель и уровень верификации интегрируются в payload JWT токена для минимизации количества запросов к базе данных при проверке прав доступа.

## 5. Система верификации и гейты доступа
Система имеет 4 уровня верификации, определяющие уровень доступа пользователя (хранится в колонке `verification_level` таблицы `users`):
* **Level 0:** Регистрация по телефону (Разрешен только просмотр каталога и ленты).
* **Level 1:** Подтверждение email и телефона.
* **Level 2:** Предоставление ИНН / паспортных данных. **Важно:** Взаимодействие с таблицами `requests` (заявки) и `chats` (мессенджер) на уровне RLS (Row Level Security) или API-контроллеров разрешено строго с этого уровня.
* **Level 3:** Подтверждение лицензий / сертификатов (Выдача бейджа "Проверенный").
